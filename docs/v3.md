# VersionDock Desktop V3 功能实现需求

## 1. 文档目标

VersionDock Desktop 当前 UI 视觉与主要页面结构已基本完成。V3 不再进行大规模视觉重做，工作重心从“界面还原”切换到“真实功能落地、闭环稳定与可发布验收”。

V3 的核心目标是：让所有对用户可见的非 AI 功能都具备真实 Rust Backend、稳定的 Bridge 契约、完整的前端状态流转、明确的成功或失败反馈，以及真实 Git/SVN 仓库测试证据。

本阶段不实现任何 AI 能力。

## 2. 项目与仓库边界

桌面端工程，也是唯一允许写入的目录：

```text
/Volumes/WorkSSD/Project/VersionDockDesktop
```

VersionDock 插件只作为业务规则和交互行为的只读参考：

```text
/Volumes/WorkSSD/Project/VersionDock
```

必须遵守：

- 不修改、格式化、暂存、提交、删除或推送 VersionDock 插件仓库中的任何内容。
- VersionDockDesktop 必须能够独立克隆、构建、测试和发布，运行时及构建时不得读取 VersionDock。
- 不使用跨目录 import、绝对路径依赖、npm `file:`、符号链接、Git Submodule 或运行时复制依赖插件仓库。
- 保留当前桌面端已经完成的 UI 结构和视觉成果；实现功能所需的交互状态可以调整，但不得借机重做设计系统或大范围改版。
- 当前工作区中的未提交改动均视为用户工作，必须保留；不得自动执行 `git add`、`git commit`、`git push` 或破坏性 Git 清理命令。
- 继续使用 GPL-3.0-only，并维护迁移来源与第三方声明。

## 3. V3 范围

### 3.1 必须完成

- 复核并打通现有 Git/SVN 核心工作流，修复只有界面、只有前端状态或后端行为不完整的功能。
- 完成所有保留在设置页中的非 AI 设置，使配置能持久化并真正影响运行时行为。
- 完善工作区监听、自动刷新、请求竞态、取消、超时和错误恢复。
- 完成 Git Identity Profile、SVN 账号接入和 File History。
- 对 Stash、Shelf、Changelist、Worktree、Subtree、Branch Compare、Remote Management 做真实功能验收并补齐缺口。
- 隐藏所有尚未具备完整闭环的入口；不得用禁用控件、静态假数据、浏览器 `prompt/confirm` 或“即将推出”占位冒充功能完成。
- 建立真实临时 Git/SVN 仓库的集成测试与关键前端交互测试。
- 完成 macOS 实机运行验收，并为 Windows/Linux 保留可重复的构建与运行验收清单。

### 3.2 明确不做

- AI Commit Message
- AI Commit Composer
- AI Code Review
- AI Commit Explanation
- AI Merge Conflict Resolution
- AI Provider、模型、API URL、API Key、Prompt 管理及任何 AI 网络请求
- Git Blame 编辑器内联装饰
- Git/SVN Ghost Text、VS Code TextEditor/Document 能力
- VS Code Status Bar、Activity Bar Badge、Command Palette、Editor Context Menu
- 为未来能力预先搭建无实际调用方的复杂抽象

AI 设置、AI Prompt 和编辑器注解相关区块不得出现在 Desktop 设置页中。`DesktopCapabilities.ai` 必须始终为 `false`。

## 4. 完成定义

一个功能只有同时满足以下条件，才能标记为完成：

1. UI 存在明确入口，或该功能明确属于后台自动行为。
2. React 组件只通过 `VersionDockBridge` 调用业务能力，不直接散落 Tauri `invoke()`。
3. Rust Backend 使用结构化参数执行真实 Git/SVN/系统操作，不拼接 Shell 字符串。
4. 请求具备加载、成功、失败、取消、超时和必要的二次确认状态。
5. 操作完成后只刷新受影响的数据，且旧请求不能覆盖新状态。
6. 错误能说明失败对象、原因和可恢复方式，不只显示通用“操作失败”。
7. 至少有真实临时仓库集成测试；纯前端功能还应有组件或 Store 测试。
8. 在 Tauri Runtime 中实际运行通过。MockBridge、浏览器演示数据和静态构建通过均不能单独作为功能完成证据。

如果任一条件不满足，对应入口必须隐藏，或在差距清单中明确标记为未完成。

审计至少覆盖：

- Git/SVN 仓库发现、嵌套归属、混合工作区和多仓库切换
- 文件监听、手动刷新、自动刷新和后台 Fetch
- Git status、Diff、stage、unstage、discard、commit、amend、fetch、pull、push
- SVN status、Diff、add/delete、revert、commit、update、history
- Git/SVN History、Commit Detail、文件 Diff 和多提交选择

审计中发现的问题按 P0、P1、P2 排序，随后直接处理最高优先级且边界明确的问题。

## 6. 功能要求

### 6.1 工作区与仓库生命周期

- 打开、恢复、切换工作区后立即启动正确的文件监听，不依赖用户先手动刷新。
- 切换或关闭工作区时必须停止旧 watcher、取消旧请求并释放子进程和事件订阅。
- watcher 事件需要防抖、合并和去重；忽略 `.git`、`.svn`、`node_modules`、`target`、`dist` 等高噪声目录时，不能漏掉会改变 Git/SVN 状态的关键元数据事件。
- 不允许一次文件变化触发全量 History、Branch、Tag、Stash、Shelf、Worktree 等所有数据重复加载。按事件类型和当前页面刷新受影响数据。
- 工作区切换、快速连续刷新和慢请求返回时，使用 workspace ID、repository ID 和 generation 防止旧结果覆盖新状态。
- 仓库扫描深度和忽略目录必须来自设置，不得继续使用不可配置的固定值。
- 支持空格、中文、特殊字符、嵌套仓库、Git Submodule、Git Worktree 及 Git/SVN 混合目录。
- Git 或 SVN 未安装时显示对应工具缺失状态，不得把空仓库状态误报为成功。

### 6.2 Git 核心闭环

以下功能必须逐项用真实仓库验证：

- status 正确解析 staged、unstaged、untracked、renamed、deleted、conflicted 和 submodule 状态。
- 工作区 Diff、暂存区 Diff、提交 Diff、范围 Diff 正确处理新增、删除、重命名、二进制和大文件。
- 单文件、多文件、仓库级 stage/unstage。
- discard 对 tracked 与 untracked 文件采用不同的明确确认文案，并防止越界、符号链接逃逸和误删目录。
- commit、amend、指定文件提交、多仓库提交和 Commit & Push。
- fetch、pull、push 的 upstream 缺失、分支分叉、认证失败、网络超时和远端拒绝反馈。
- History 分页、筛选、图谱拓扑、Merge Commit、Commit Detail、父提交文件和未推送提交。
- Branch 创建、切换、重命名、安全删除和强制删除。
- Tag 创建、删除、检出和推送。

多仓库提交不是事务。若部分仓库成功、部分失败，必须返回逐仓库结果，保留成功状态并明确列出失败项；不得只显示一个全局错误，也不得自动回滚已成功的真实提交。

### 6.3 SVN 核心闭环

以下功能必须使用 `svnadmin` 创建真实临时仓库验证；本机缺少工具时只允许显式跳过，不得记为通过：

- checkout 后的 status、Diff、add、delete、revert、commit、update。
- revision history、revision detail、文件历史和两个 revision 之间的 Diff。
- textual、property、tree 和 obstruction conflict 的识别与呈现。
- resolve 前验证工作副本状态，resolve 后刷新状态和历史。
- update/commit 的认证失败、out-of-date、working copy locked 和网络错误反馈。
- 路径包含空格、中文和特殊字符时仍能正确工作。

Git 专属能力不得显示在 SVN 仓库上；SVN 不支持的操作必须由 capability 隐藏，而不是点击后报错。

### 6.4 冲突与 Merge Editor

- Git 和 SVN 冲突列表必须来自真实仓库状态。
- 文本冲突需要加载 Base/Mine/Theirs/Working，保留现有 3-way Merge Editor，并在保存时校验 fingerprint，防止覆盖外部修改。
- Git resolve 后执行正确的 stage；SVN resolve 后执行对应 `svn resolve`。
- 二进制冲突只提供 Mine/Theirs/Working 整体选择，不进入文本编辑器。
- property conflict、tree conflict 或无法自动提供三份文本的情况必须显示其真实类型与可执行动作，不能伪装成普通文本冲突。
- 中止 merge/rebase/cherry-pick 等操作属于破坏性行为，必须明确识别当前 operation 并二次确认。

### 6.5 扩展 Git 能力

现有入口必须逐一完成真实验证：

- Stash：create、apply、pop、drop、include untracked、按文件创建；冲突和脏工作区失败需保留现场。
- Shelf：create、部分/全部 apply、drop；补丁和元数据写入应用数据目录，写入采用原子替换，失败不得丢失 Shelf。
- Changelist：create、rename、delete、assign、remove；元数据与当前仓库文件状态一致，文件消失或重命名时可恢复。
- Worktree：list、create、remove、lock、unlock、prune；路径不能逃逸管理范围，强制删除必须二次确认。
- Subtree：register/add、pull、push、unregister、pending recovery；必须校验 prefix、remote、branch 和中断恢复状态。
- Branch Compare：提交集合、文件集合、增删统计和 Diff 必须基于真实 base/target。
- Remote Management：list、add、rename、set fetch URL、set push URL、remove、prune；敏感 URL 不写入日志。

每项能力应根据仓库类型、工具可用性和运行条件动态计算 capability。Backend、测试或错误恢复不完整时，暂时关闭对应 capability。

### 6.6 Git Identity Profile

- 支持读取当前仓库 local identity 和 Git global identity。
- 支持创建、编辑、删除和选择自定义 Profile，至少包含 `user.name` 与 `user.email`。
- 明确显示当前提交实际会采用的 identity 及其来源：custom、local 或 global。
- 提交前无法解析有效 identity 时阻止提交并给出可操作提示。
- 自定义 Profile 作用于本次 Git 命令，不得在用户未确认时改写仓库或全局 `.gitconfig`。
- Profile 数据存储在标准应用数据目录；如果未来加入 signing key、Token 等敏感信息，必须进入系统安全存储，不能写入普通 JSON。
- 多仓库提交时逐仓库解析 identity，不能错误复用当前选中仓库的配置。

### 6.7 SVN 账号

- 支持按 SVN repository root 保存和选择用户名配置，并允许测试连接。
- 密码不得写入 `state.json`、普通配置、日志、错误对象或测试快照。
- 密码只允许存入系统安全凭据存储；调用 SVN 时优先使用支持 stdin 的安全输入方式或系统 SVN credential cache。
- 如果当前 SVN 版本无法避免在进程参数中暴露密码，则不得降级为明文参数；应提示用户使用系统 SVN 凭据缓存，并保持密码保存 capability 关闭。
- 认证失败、证书问题和账号权限不足必须分开反馈，不得统一显示为网络错误。
- 自动化测试使用临时凭据和临时仓库，不读取用户真实认证数据。

### 6.8 File History

- 从 Commit Panel、Commit Detail 和 Diff 页面均可打开文件历史。
- Git 支持跟随 rename 的文件日志、指定提交的文件内容和相邻版本 Diff。
- SVN 支持文件 revision history、revision 内容和相邻 revision Diff。
- 文件历史分页加载，切换文件或仓库时取消旧请求，旧结果不得串入新页面。
- 删除文件、二进制文件、大文件和历史中发生路径变化时给出准确状态。
- File History 使用真实 Backend 数据，不复用整仓库历史后在前端做不可靠过滤。

## 7. 非 AI 设置必须生效

设置页只保留 Desktop 能够实现的配置。V3 至少完成：

- Changes display mode：保留适用于 Desktop 的 `simplified` 与 `changelists`；移除 `VS Code native`。
- Default commit action：`commit` / `commitAndPush`。
- Default save action：`stash` / `shelf`。
- Prompt before adding untracked files。
- Suppress diverged branch warning。
- Auto-refresh interval，`0` 表示关闭。
- Fetch on startup。
- Reset view locations on startup。
- Notify on incoming commits。
- Notify on unpushed commits。
- Repository scan depth。
- Ignored folders。
- Maximum graph commits。
- Project colors。
- Theme、language、UI font size、file view、stash view、面板宽度和折叠状态。
- External editor executable 与逐行参数模板。

实现要求：

- 配置集中定义类型、默认值、校验、迁移和持久化，不在组件内散落魔法值。
- 读取旧状态时补默认值并校验非法值；升级不能导致应用启动失败。
- 配置更改后即时生效；需要重扫仓库或重载 History 时只执行必要刷新。
- `Project colors` 应提供结构化编辑体验，不要求用户直接编辑 JSON。
- 系统通知必须去重，只在状态从无到有或数量增加时触发；首次启动不得把全部历史状态当成新通知。
- OS 通知权限不可用时回退为应用内通知，并明确显示权限状态。
- 移除全部 AI 设置和 AI Prompt 区块。
- 移除 Git annotations、Git ghost text 等依赖 VS Code Editor 的设置。

## 8. Bridge、状态与错误处理

- Rust 是数据契约的单一来源，通过 Specta 生成 TypeScript bindings，并在构建中执行一致性检查。
- `VersionDockBridge` 继续统一封装 requestId、超时、AbortSignal、取消、进度和事件订阅。
- Progress 事件必须反映真实阶段；不能对所有命令只发送固定的 started/finished 文案来冒充进度。
- 对长任务显示可取消状态，并在 Rust 中真正终止等待与子进程。
- 同一 repository 的写操作串行化；不同 repository 可以有限并行。
- 只读任务限制并发，避免大工作区启动时同时拉起过多 Git/SVN 进程。
- Store 不直接原地修改嵌套 bootstrap state；所有更新保持不可变，防止 React 订阅失效。
- 不使用单个全局 `busy` 阻塞整个应用。至少区分 workspace、repository、history、diff、commit、sync 和扩展功能的进行中状态。
- 错误结构继续保留 `code`、`message`、`command`、`exitCode`、`stderr`、`recoverable`，并增加足够的 operation/repository 上下文供 UI 展示。
- UI 默认展示用户可理解的摘要，允许展开技术详情；任何密码、Token、Authorization Header 和含凭据 URL 必须脱敏。

## 9. 安全与破坏性操作

- 所有用户输入使用 `command + args + cwd` 执行，不经过 Shell。
- Backend 必须重新解析 workspace ID 和 repository ID，不能信任前端传入的绝对路径。
- 用户文件路径必须是仓库内相对路径，拒绝绝对路径、`..`、NUL 和符号链接祖先逃逸。
- discard、revert、force delete branch、drop stash/shelf、remove worktree、remove remote、冲突整体覆盖和中止操作必须二次确认。
- 确认框必须列出实际影响对象和不可恢复后果；不要只写“确定吗”。
- 能避免数据丢失时优先提供安全模式，并把 force 作为显式第二选择。
- 状态文件、Shelf、Changelist、Profile 等应用数据使用原子写入；写失败时保留旧文件。
- 测试只能操作临时目录，不得读取或修改用户真实仓库、Git 全局配置、SVN 凭据或系统 Keychain 内容。

## 11. 执行顺序

每完成一个阶段，报告：

- 已完成的真实行为变化

## 12. 验证命令
