# VersionDock Desktop V4 后续工作需求

## 1. 文档目标

V4 以当前 VersionDock Desktop 源码为唯一基线，只记录已经通过源码确认的后续缺口，不重复实现现有功能，也不根据猜测扩展产品范围。

下文第 4、5 节保留最初审计时的问题描述，当前完成状态以第 11 节为准。

后续实施遵循以下原则：

- 已经存在并生效的功能只做必要回归，不重新设计或重写。
- VersionDock 插件仅用于只读核对交互和业务规则，Desktop 必须保持独立。
- 新增待办必须能指向当前源码缺口、真实运行问题或明确的发布验收要求。
- 内部重构只服务于已确认的问题，不把技术名词包装成新的用户功能。
- 不重做视觉系统，不改变已经验收通过的状态栏、Diff 面板和主要页面布局。

## 2. 明确不做

V4 不实现以下内容：

- 任何 AI 功能、AI 设置、Provider、Prompt、API Key 或 AI 网络请求。
- Git/SVN Ghost Text。
- Git/SVN Blame。
- 独立 Submodule 标签、独立 Submodule 面板或新的 Submodule 管理中心。
- 依赖 VS Code Extension Host 的 Editor API、Activity Bar、Command Palette 等宿主集成。
- 自动升级系统，以及没有单独确定发布目标的签名、公证扩项。
- 只有占位 UI、Mock 数据或无实际调用方的未来抽象。

VersionDock Desktop 自有状态栏和 Diff 显示面板已经存在，不属于本节排除内容，也不在 V4 中重新实现。

## 3. 已确认完成的基线

以下能力在当前源码中已经存在，V4 不得再按“从零实现”立项：

- Desktop 状态栏、分支菜单、Profile 菜单和通知中心。
- 工作树、暂存区、提交、范围、Branch Compare、File History、二进制和大文件 Diff 显示组件。
- Project colors 持久化及实际渲染：Rust 扫描将配置写入 `RepositoryMeta.color`，History、Commit Detail、Branch、Status、Shelf、Push 等界面已消费该颜色。
- Bridge 请求超时、AbortSignal、Rust CancellationToken 和子进程 `kill_on_drop`。
- Backend 同仓库写操作串行锁和只读命令并发上限。
- 结构化 `DesktopError` 及 operation、workspace、repository、subject、hint 上下文。
- Git Identity Profile、SVN Account、系统 `keyring` 和 SVN `--password-from-stdin` 安全传递。
- incoming/unpushed 通知基线、系统通知权限请求、通知中心记录和应用内回退。
- 批量提交 Backend 逐仓库 `RepositoryOperationResult`。
- Submodule 扫描、Backend Init/Update/Deinit/Sync、分支状态菜单和 gitlink 最小右键菜单。
- 多工作区标签、多窗口打开和跨窗口标签拖放。

这些功能仍需随相关修改执行回归测试，但除下文明确指出的问题外，不扩展新的面板、菜单或交互概念。

## 4. P0：已确认的功能缺口

### 4.1 修复 Submodule 分支菜单的真实执行目标

当前 Desktop 的 Submodule 分支菜单已经显示，但调用参数与 Backend 契约不一致：

- `BranchMenuPopover` 使用 Submodule 子仓库 ID 调用 `submoduleOperation`。
- operation 的 `path` 传入子仓库绝对 `rootPath`。
- Backend 实际要求父仓库 ID，以及父仓库 `.gitmodules` 中声明的相对 gitlink 路径。

V4 必须修复这一真实问题：

- Init、Update、Update Recursive、Deinit 均以父仓库为执行仓库。
- Submodule 路径使用经过 Backend 校验的仓库内相对路径，不传绝对路径。
- “在新窗口打开”必须调用 VersionDock Desktop 的新窗口能力；当前 `systemOpen(..., reveal: true)` 只是文件管理器定位，行为不符合菜单名称。
- 操作完成后刷新父仓库 gitlink 状态和对应 Submodule 仓库状态。
- 增加前端契约测试和真实 Git Submodule 集成测试，防止菜单存在但真实命令失败。

不新增独立 Submodule 标签或面板。gitlink 文件右键继续与 VersionDock 一致，只保留 Stage/Unstage 和 Refresh，不增加 Submodule 管理菜单。

### 4.2 展示批量 Commit / Commit & Push 的逐仓库结果

Backend 已返回 `committed`、`revision`、`pushed` 和结构化 `error`，但 Store 当前只把失败项拼成全局错误，Commit Panel 也会在部分失败后清空全部提交信息和选择。

V4 需要：

- 显示每个仓库的 commit、revision、push 和失败阶段。
- 部分成功时保留成功事实，不回滚已经产生的提交。
- 失败仓库保留提交信息和文件选择，成功仓库可以清理已完成状态。
- Commit 成功但 Push 失败时提供只重试 Push 的入口，不重新 Commit。
- 结果模型直接使用现有 Rust/Specta 契约，不再创建第二套前端结果格式。

### 4.3 去除全局 `busy` 造成的无关界面阻塞

Backend 已有正确的仓库写锁和并发限制，缺口位于前端：Store 虽然记录了 domain 计数，多个面板仍直接读取全局 `busy`，导致一个仓库操作时禁用其他仓库或无关面板。

V4 只需要解决这个实际问题：

- 以现有 operation domain 为基础补充 repository 维度。
- 按钮只读取与自身操作相关的 loading 状态。
- 保留必要的应用级状态，例如启动和工作区切换；不要求为所有短请求建立复杂任务对象。
- 不重复实现 Backend 已有的写锁、CancellationToken 或并发信号量。

### 4.4 Watcher 按仓库和数据范围精确刷新

当前 watcher 能识别 `worktree`、`status`、`refs` 并防抖，但 Backend 实际发出 workspace 级 `WorkspaceEvent`；Store 收到任一事件后先执行完整 `refresh(true)`，refs 事件还会额外重载 History 和当前仓库。

V4 需要：

- watcher 事件定位实际受影响的 repository。
- 事件携带明确刷新范围，至少区分 status/diff、refs/history 和仓库重新扫描。
- 普通文件变化只刷新对应仓库 status 和当前相关 Diff。
- Git HEAD/refs、index、operation 元数据和 SVN `wc.db` 只触发各自必要的数据刷新。
- 保留现有 `.git/.svn` 元数据监听、忽略目录过滤、防抖、generation 和 watcher 生命周期能力。
- 多个短时间事件合并后仍只刷新受影响仓库，不退化为整个工作区全量刷新。

### 4.5 补齐 File History“加载更多”的取消与上下文校验

File History 初始历史、revision 内容和相邻 Diff 已使用 AbortController；只有 `loadMore()` 仍未传入 AbortSignal，也未在响应写入前核对当前 workspace/repository/path。

V4 需要：

- `loadMore()` 使用 AbortController。
- 切换文件、仓库、工作区或关闭面板时取消旧分页请求。
- 追加结果前核对当前 workspace、repository、path 和 cursor 上下文。
- 保留现有 Git/SVN 分页契约，不重新设计 File History 面板。

## 5. P1：基础设施收口

### 5.1 处理未被消费的 Progress 事件

当前 Rust 只在命令入口发一个初始 phase，再发 completed/failed；前端 Bridge 转发 `ProgressEvent`，但 Store 和 UI 没有消费它。

V4 不要求为所有命令制造复杂进度系统，只能选择以下一种长期一致的方案：

1. 对扫描、Fetch/Pull/Push、批量提交、Subtree 等确实耗时的操作发送少量真实阶段，并在相关界面展示；或
2. 如果产品不需要阶段进度，删除未消费的 Progress 契约，继续使用局部 loading 和现有取消机制。

禁止保留固定 started/completed 事件并将其当作真实进度，也禁止伪造百分比。

### 5.2 修正功能可用性标记的真值

`RepositoryCapabilities` 是内部契约，不是用户功能。当前按 VCS 类型和工具可用性区分 Git/SVN 已经满足主要入口需求，不需要设计复杂规则引擎。

V4 只修正确认存在的问题：

- Bootstrap 中 `secure_credentials` 和 `system_notifications` 不再硬编码 `true`；应返回真实平台状态，或删除未被使用的字段。
- UI 只在实际依赖该能力的入口读取对应标记。
- Git/SVN 工具缺失时继续使用现有 repository capability 隐藏不可用操作。
- 不根据“是否有测试”在 Runtime 动态开关功能；测试结果属于发布验收，不是运行时仓库状态。

### 5.3 国际化遗漏收口

当前仍有已确认的硬编码可见文本，例如：

- `App.tsx` 的 `Technical details`。
- `IgnoreRulesPanel.tsx` 的 `Manage Ignore Rules`、`Loading…`、`One pattern per line`。
- Commit/Discard/Delete 和通知正文中的部分英文句子。

V4 需要将这些文本接入现有 `t(...)`，并检查右键菜单、确认框、错误详情和通知正文。只修复真实可见文本，不翻译 Git/SVN 原始输出、命令、路径和专有名词。

## 6. 现有界面与多窗口回归

本节是回归范围，不是新增功能或视觉重做。

### 6.1 右键菜单和 Diff

- 保持当前已经验收的菜单名称、目标类型和排列，不凭空增加 VersionDock 中不存在的菜单项。
- 验证文件、目录、仓库、分支、提交和历史文件的单选/多选目标没有串仓库、路径或 revision。
- 验证工作树、暂存区、提交、范围、Branch Compare、File History、二进制和大文件 Diff 在相关状态改造后仍可打开。
- 保持现有语法颜色、增删背景、空白斜纹、横向滚动和长行裁剪，不重新设计 Diff 页面。
- 保持 Desktop 自有状态栏及现有样式，不按 VS Code 宿主状态栏重新实现。

### 6.2 多工作区和跨窗口拖放

只验证用户可观察行为：

- 标签在当前窗口、新窗口和另一个已打开窗口之间移动后，工作区内容与选中状态正确。
- 拖放成功时源窗口移除对应标签，失败或取消时源窗口保留标签。
- 关闭或恢复窗口后不出现重复标签、丢失标签或串用其他工作区状态。
- 跨窗口操作后 watcher、自动刷新和通知不出现明显重复执行。

不在 V4 中预先规定多窗口内部必须“共享”还是“隔离” Store、watcher 或通知状态；实现以满足上述行为和不重复执行真实操作为准。

## 7. 跨平台 Runtime 与发布验收

当前 CI 和 Release workflow 已配置生成 macOS universal、Windows x64 和 Linux x64 安装包。V4 后续是验证这些构建产物能够实际安装和运行，而不是再次搭建打包流程。

至少记录：

- macOS universal：Apple Silicon/Intel 启动边界、Git/SVN、Keychain、通知和中文/空格路径。
- Windows x64：安装/卸载、WebView2、Credential Manager、通知和包含 Unicode argv 修复的 SVN CLI。
- Linux x64：实际生成的 AppImage/deb/rpm、WebKit2GTK、Secret Service、通知及依赖缺失反馈。
- Git/SVN 混合工作区、嵌套仓库、Submodule、Worktree、复杂冲突和 watcher 长时间运行。

没有实际运行的平台只能记录“构建通过、Runtime 未验收”，不得标记为功能完成。签名、公证和自动升级如果未来需要，应另立发布需求，不在 V4 中默认展开。

## 8. 测试要求

### 8.1 定向测试

- Submodule 分支菜单必须断言父仓库 ID、相对路径和真实操作结果。
- 批量提交覆盖全部成功、Commit 失败、Commit 成功但 Push 失败和多仓库部分成功。
- Store 覆盖跨仓库局部 loading，确保无关仓库按钮不被禁用。
- Watcher 覆盖 repository 定位、refresh scope、事件合并和旧 generation 丢弃。
- File History 覆盖加载更多期间切换文件、仓库、工作区和关闭面板。
- 国际化测试覆盖本轮清理的可见硬编码文本。
- 多窗口测试覆盖标签导入、完成回执、取消和源窗口回退。

### 8.2 持续质量门禁

每个阶段至少执行：

```text
npm run check
git diff --check
```

涉及 Git/SVN 行为时运行真实临时仓库集成测试；发布阶段执行实际安装包 Runtime 验收。环境缺少 Git/SVN 时必须输出明确 SKIP 原因，且该项不计入完成。

## 9. 建议执行顺序

1. 修复 Submodule 分支菜单的父仓库/相对路径和新窗口行为。
2. 展示批量 Commit / Commit & Push 的逐仓库结果并保留失败上下文。
3. 将全局 `busy` 的 UI 使用改为仓库/操作域局部状态。
4. 将 watcher 刷新缩小到受影响仓库和数据范围。
5. 补齐 File History `loadMore()` 取消与上下文校验。
6. 决定 Progress 事件接入或删除，并修正 Bootstrap 能力真值。
7. 清理确认存在的国际化遗漏。
8. 完成菜单、Diff、多窗口和三平台 Runtime 回归。

## 10. 最终验收标准

V4 完成时应满足：

- Submodule 不出现独立标签或面板，现有分支菜单操作能在真实仓库正确执行。
- 批量提交完整展示每个仓库结果，部分失败不会丢失失败仓库上下文。
- 一个仓库执行操作不会无故阻塞其他仓库和无关面板。
- watcher 不再因单仓库普通变化无差别刷新整个工作区。
- File History 加载更多不会把旧文件或旧仓库结果追加到当前面板。
- Progress 契约被真实消费或被删除，不保留虚假进度。
- 功能可用性标记反映实际工具和平台状态，不硬编码安全凭据或系统通知可用。
- 已确认的可见硬编码文本完成中英文收口。
- 状态栏、Diff、右键菜单和多窗口现有行为没有因 V4 改造回退。
- CI 继续通过；实际运行过的平台记录 Runtime 证据，未运行的平台如实标记边界。
- AI、Git/SVN Ghost Text、Git/SVN Blame 始终不在 V4 范围内。
