# VersionDock Desktop V4 后续工作需求

## 1. 文档目标

V4 以当前代码为唯一基线，目标不是重做界面或再次罗列已经完成的功能，而是收口现有非 AI 能力的运行真实性、并发安全、局部刷新、错误恢复和跨平台发布质量。

当前主要 Git/SVN 页面、Diff、History、Commit Detail、分支比较、工作树差异、右键操作、多工作区、多窗口、Identity、Remote、通知中心以及扩展 Git 功能已经具备基础实现。V4 只处理经过当前源码审计仍存在的闭环缺口和发布风险。

文档基线：

- 前端自动化基线：25 个测试文件、160 个测试通过。
- Rust 自动化基线：45 个测试通过，真实 Git/SVN 用例未静默跳过。
- 当前 `docs/` 仅保留 `v1.md`、`v2.md`、`v3.md`，V4 不恢复已经清理的临时审计文档。

测试通过仅代表自动化基线，不等同于所有平台、权限、安装包和真实复杂仓库场景均已完成验收。

## 2. 项目边界

唯一允许写入的工程：

```text
~/Project/VersionDockDesktop
```

VersionDock 插件仓库仅作为只读交互和业务规则参考：

```text
~/Project/VersionDock
```

必须继续满足：

- Desktop 独立构建、测试和运行，不引入跨仓库运行时依赖。
- 不修改、格式化、清理、暂存、提交或推送 VersionDock 插件仓库。
- 不覆盖用户未提交改动，不自动执行 `git add`、`git commit` 或 `git push`。
- 保持 GPL-3.0-only，并维护第三方依赖与迁移来源声明。
- 不重做现有视觉系统；只修复影响可用性、一致性和跨平台运行的界面问题。

## 3. 明确不做

V4 不实现以下功能：

- 任何 AI 功能、AI 设置、Provider、Prompt、API Key 或 AI 网络请求。
- Git/SVN Ghost Text。
- Git/SVN Blame。
- 独立 Submodule 标签、独立 Submodule 面板或新的 Submodule 管理中心。
- VS Code Editor、Status Bar、Activity Bar、Command Palette 等宿主专属能力。
- 只有占位 UI、Mock 数据或无实际调用方的未来抽象。

Submodule 继续作为 Git 仓库和 gitlink 文件的一部分呈现。保留 VersionDock 已有的 Submodule 命令、分支状态菜单操作，以及 gitlink 文件右键中的 Stage、Unstage 和 Refresh；不扩展为文件、目录或仓库右键管理菜单，也不新增独立入口。

## 4. V4 完成定义

一项后续工作只有同时满足以下条件才算完成：

1. Rust Backend 执行真实操作，Bridge 契约和前端状态与结果一致。
2. 加载、成功、部分成功、失败、取消和超时均有明确状态。
3. 同仓库写操作不会并发破坏状态，旧请求不会覆盖新工作区或新仓库结果。
4. 操作后只刷新受影响的数据域，不使用无差别全量刷新掩盖状态问题。
5. 错误包含操作对象、仓库和恢复建议，且凭据、Token、认证头和含密码 URL 已脱敏。
6. 有真实临时 Git/SVN 仓库测试；涉及系统能力时有对应平台实机证据。
7. 在 Tauri Runtime 或真实安装包中完成验收。

这里的“功能完成”和“发布验收完成”分别记录：代码、自动化和当前平台 Runtime 通过后可标记功能完成；只有声明支持的平台都具备真实安装证据后，才可标记 V4 发布验收完成。CI 构建结果只能证明可构建，不能自动提升为实机验收证据。

`BrowserDevBridge`、浏览器演示、类型检查、静态构建或 CI 产出安装包都不能单独作为 Runtime 功能完成证据。无法满足完成定义的 capability 必须关闭或隐藏。

## 5. P0：操作状态与并发安全

### 5.1 结构化操作状态

移除单个全局 `busy` 对整个应用的联动控制，建立按 workspace、repository 和 domain 隔离的 `OperationState`。至少覆盖：

- workspace 扫描与切换
- status 与 Diff
- History、Branch、Tag 和 Commit Detail
- commit、save、sync 和批量操作
- conflict 与 operation abort
- Stash、Shelf、Changelist、Worktree、Subtree、Remote
- Identity、SVN Account 和 File History

状态至少包含 operation ID、目标仓库、阶段、开始时间、是否可取消、进度、结果和结构化错误。同一仓库的写操作串行执行；不同仓库允许受限并行；只读操作设置统一并发上限。

V4 固定采用每仓库 FIFO 写队列、最多 2 个仓库并行写、最多 4 个只读操作并行。请求等待写锁或并发许可期间也属于可取消阶段。

局部按钮只由相关操作状态禁用。仓库 A 正在 Fetch 时，不得阻止仓库 B 查看 Diff、切换历史或编辑设置。

### 5.2 请求 generation 与取消

- workspace、repository、history、diff、file-history 等请求带 context generation；context 同时携带 `foreground` / `background` 可见性，供所有窗口统一决定是否展示进度。
- 切换工作区、仓库、文件、revision 或关闭面板时取消旧请求。
- Backend 无法及时取消的旧响应必须由 Store 丢弃，不能写入当前页面。
- 可取消命令必须真正终止子进程及等待链，不能只让前端停止显示加载状态。
- 应用退出、窗口关闭和工作区卸载时释放定时器、watcher、订阅和子进程。

## 6. P0：真实进度与 Watcher 精确刷新

### 6.1 命令真实阶段

现有 Progress 事件需要从“命令开始/结束”升级为实际执行阶段。例如：

- 扫描：枚举目录、识别仓库、读取元数据、生成快照。
- History：解析 refs、加载 commits、构建拓扑、投影当前页。
- Commit & Push：校验、解析 identity、提交、刷新状态、推送、读取远端结果。
- SVN：认证准备、执行 update/commit、解析冲突、清理 working copy 状态。
- 扩展操作：准备、执行、恢复检查、刷新受影响数据。

前端应消费这些阶段，在对应面板展示进度和取消入口；短操作无需制造虚假百分比。全局操作反馈固定放在底部状态栏，不使用遮挡工作区内容的右上角浮层或顶部动画线；状态栏显示阶段、真实进度、并发数量和取消入口，并在紧凑窗口下截断文案、隐藏次要进度元素。

进度可见性必须区分用户发起的前台操作与系统发起的后台读取。Watcher、自动刷新、通知基线、启动后的辅助加载等后台读取可以保留内部 operation context 用于并发、取消和诊断，但不得进入全局进度条、`aria-live` 状态提示，也不得禁用 Commit、Branch 或其他交互控件。后台刷新失败不得用反复出现的前台进度提示掩盖；只有用户显式触发的操作和需要用户等待或取消的长任务展示可见进度。

Bridge 的默认策略采用前台操作白名单：写操作、同步、工作区扫描以及确实需要用户等待或取消的任务默认可见；status、identity、账户摘要、refs 列表、窗口同步和面板辅助查询等纯读取默认后台。组件可以显式提升需要展示的读取任务，但不得依赖每个后台调用方逐一记得关闭进度。

### 6.2 RepositoryEvent 与刷新范围

Watcher 事件需要包含 workspace ID、repository ID、generation、事件来源和明确 refresh scope。至少区分：

- 工作文件变化：刷新 status 和当前相关 Diff。
- Git index 变化：刷新 staged/unstaged、冲突和 Commit Panel。
- `HEAD` 或 refs 变化：刷新 Branch、Tag、History、未推送和分歧状态。
- merge/rebase/cherry-pick 元数据：刷新 operation 与冲突状态。
- SVN `wc.db` 或元数据：刷新 status、冲突、revision 和必要历史。
- 仓库新增、删除或移动：按扫描范围更新 workspace snapshot。

事件应防抖、合并和去重，但不能因忽略普通高噪声目录而漏掉 `.git`、`.svn` 的关键元数据。自动刷新与启动 Fetch 使用独立调度器，不依赖全局 `busy`，修改间隔、切换工作区或退出时可靠清理。

## 7. P1：Capability、通知与安全凭据真值

### 7.1 仓库功能可用性判断

Backend 可以继续使用 `RepositoryCapabilities` 作为内部契约，但界面上的功能可用性不能只根据 VCS 类型和工具是否存在直接全开。每项能力需要综合：

- 当前平台和 Git/SVN 版本
- 仓库、工作副本和 operation 状态
- 所需系统依赖与安全存储是否可用
- Backend、错误恢复和真实集成测试是否完整
- 当前路径或管理范围是否满足安全限制

未满足条件的入口必须隐藏或给出明确不可用原因，不能点击后才发现是占位实现。`DesktopCapabilities.ai` 始终为 `false`。

### 7.2 系统通知

- Bootstrap 返回真实通知支持状态和当前权限状态，不硬编码可用。
- 权限状态至少区分未请求、允许、拒绝、受系统限制和不可用。
- 系统通知不可用时回退应用内通知，并在设置页说明原因和恢复方法。
- incoming/unpushed 通知按稳定 repository ID 保存基线，仅在从无到有或数量增加时触发。
- 多窗口共享通知去重状态，避免每个窗口重复弹出。

### 7.3 SVN 安全凭据

- Bootstrap 返回真实安全存储能力，不硬编码可用。
- macOS Keychain、Windows Credential Manager、Linux Secret Service 分别验证读写、删除、拒绝权限和不可用场景。
- 安全存储抽象提供内存测试实现，自动化测试不得读取用户真实凭据。
- 只有 SVN 版本支持安全 stdin 输入且安全存储可用时，才开放保存密码能力。
- 不得降级为 `--password` 明文参数；不可保存时只保留用户名与系统 SVN credential cache 路径。
- 密码不得进入日志、错误、URL、事件、快照或崩溃报告。

## 8. P1：现有功能闭环补强

### 8.1 Project colors 实际生效

Project colors 当前不仅要能持久化，还必须成为真实渲染输入：

- 使用稳定 workspace/repository ID 映射颜色，不以可变名称作为主键。
- 仓库条、History 图谱、状态栏及其他已有项目标识使用同一颜色来源。
- 删除或迁移工作区时清理或迁移无效映射。
- 深色、浅色和高对比环境下保持可辨识度，非法颜色由 Backend 规范化。

### 8.2 File History 分页与上下文隔离

- 初始历史、加载更多、revision 内容和相邻版本 Diff 使用同一 AbortSignal/context generation 规则。
- 切换文件、仓库、工作区或关闭面板时，旧分页和内容请求不得继续写入状态。
- pagination cursor 必须绑定 repository、path 和当前筛选上下文，拒绝跨目标复用。
- rename、delete、binary、large file 和 SVN peg revision 状态在分页追加后保持一致。

### 8.3 批量 Commit 与 Commit & Push 结果

批量操作不是事务，必须显示逐仓库结果：

- 是否完成 commit
- 新 revision/commit ID
- 是否尝试 push
- push 是否成功
- 失败阶段、错误和恢复建议

部分仓库成功时保留真实成功事实，不回滚、不折叠成单个全局错误。用户应能只重试失败的 push 或失败仓库，并能从结果直接定位对应仓库。

### 8.4 Submodule 现有能力一致性

不新增独立标签或面板，只对齐并验证 VersionDock 已有能力：

- gitlink 状态和 Diff 展示准确，不把 Submodule 当普通文本文件读取。
- gitlink 文件右键按 staged 状态提供 Stage 或 Unstage，并保留 Refresh。
- Submodule 命令和分支状态菜单提供 Init、Update、Update Recursive、Deinit，以及 Desktop 对应的在新窗口打开能力。
- 不新增 VersionDock 中不存在的 Submodule 文件、目录或仓库右键管理菜单。
- 操作前后展示目标路径、当前 commit、预期变化和失败恢复信息。
- nested、未初始化、detached、dirty、missing URL 和认证失败场景不得导致整个 workspace 刷新失败。
- 操作后只刷新对应仓库、父仓库 status 和必要的 History/refs。

### 8.5 右键菜单与 Diff 回归

不扩展新的菜单概念，继续以当前 VersionDock 交互为基准：

- 文件、目录、仓库、分支、提交、Diff、历史文件等目标分别建立可测试的菜单矩阵。
- 菜单项的显示、禁用、危险确认和执行目标必须由实际 selection 与 capability 决定。
- 单选和多选操作不得串用错误路径、revision 或 repository。
- 所有保留菜单项都必须有真实 Backend 行为和国际化文案。
- 工作树、暂存区、提交、范围、Branch Compare、File History、二进制和大文件 Diff 继续做统一回归，保证语法颜色、增删背景、空白斜纹、横向滚动和长行裁剪一致。

## 9. P1：多工作区与多窗口回归

当前多工作区标签和跨窗口拖放需要补足生命周期验证：

- 跨窗口移动标签后只有目标窗口持有活动 watcher、订阅和自动刷新任务。
- 同一 workspace 在多个窗口打开时共享或隔离状态的规则必须明确，不重复执行破坏性写操作。
- 窗口关闭、异常退出、恢复和重新打开时不残留失效 session。
- 拖放过程中 workspace ID、选中仓库、History scope、Diff 目标和面板布局不串位。
- 多窗口通知、Fetch on startup 和自动刷新去重。
- 活动窗口执行写操作时，其他窗口及时收到精确 RepositoryEvent 并更新相关区域。

## 10. P2：国际化、可访问性与错误呈现

### 10.1 国际化收口

- 清理剩余硬编码界面文本，包括 Error Details 和 Ignore Rules 等区域。
- 右键菜单、确认框、错误恢复提示、进度阶段和系统能力状态全部进入统一词条。
- 中英文切换后已打开的 Dialog、菜单、状态栏和通知即时更新。
- 增加自动扫描或测试，阻止新增可见硬编码英文。
- 技术字段、Git/SVN 原始输出和专有名词不做误导性翻译。

### 10.2 可访问性与紧凑窗口

- 所有图标按钮、菜单、Dialog、树节点和可拖动分隔条具备正确 accessible name。
- 键盘可完成菜单打开、选择、关闭、Diff 导航和确认取消。
- 焦点在 Dialog 打开时受控，关闭后回到触发元素。
- 危险操作不能只用颜色区分；Diff 增删状态兼顾色觉差异。
- 长路径、长分支名、长代码和多仓库结果不得穿透容器。

## 11. 跨平台安装包与 Runtime 验收

CI 构建通过不等于可发布。V4 必须记录以下真实安装与运行边界：

### macOS

- Apple Silicon 与 Intel 安装、首次启动、通知权限和 Keychain。
- 签名、公证、升级、外部编辑器和 Finder 打开行为。
- Git/SVN 混合工作区、中文/空格路径及 watcher 长时间运行。

### Windows

- 安装/卸载、WebView2、Credential Manager、系统通知和升级。
- Windows SVN Unicode CLI、中文/空格/长路径、盘符和 UNC 边界。
- 文件占用、杀毒软件延迟、working copy lock 和 watcher 重命名事件。

### Linux

- AppImage、deb、rpm 至少覆盖声明支持的发行版。
- WebKit2GTK、Secret Service、桌面通知和外部文件管理器。
- 缺少 keyring、无图形会话或依赖版本不满足时给出明确降级状态。

每个平台记录安装包版本、OS/架构、Git/SVN 版本、测试 fixture、通过项、失败项和可复现步骤。没有实际执行的平台不得标记为“已验收”。

## 12. 测试要求

### 12.1 Rust

- operation coordinator、同仓库写串行、跨仓库并发上限。
- 子进程取消、超时、退出时清理和中断恢复。
- Watcher event scope、合并去重、generation 和生命周期。
- capability 计算、通知权限、安全凭据状态和敏感信息脱敏。
- 批量部分成功、File History cursor、Submodule 特殊状态。
- 特殊路径、符号链接边界、二进制、大文件和复杂 Git/SVN 冲突。

### 12.2 前端

- 局部 OperationState，不再依赖全局 `busy`。
- 旧响应丢弃、AbortSignal、订阅和定时器清理。
- 精确 watcher refresh，不发生无关面板全量重载。
- 批量结果、通知回退、capability 隐藏和系统状态说明。
- Project colors 消费、右键菜单矩阵、Diff 类型矩阵和国际化扫描。
- 多窗口标签移动、状态同步和关闭恢复。

### 12.3 持续验收

每个阶段至少执行：

```text
npm run check
git diff --check
```

涉及 Rust 或真实 VCS 行为时执行完整 Rust 测试和 Git/SVN fixture；发布阶段执行三平台构建及实际安装包验收。环境缺少 Git/SVN 时必须输出明确 SKIP 原因，且该项不计入完成。

## 13. 建议执行顺序

1. 建立按 repository/domain 的 OperationState、generation、取消和并发协调器。
2. 改造真实 Progress 阶段和前端消费。
3. 将 Watcher 升级为 RepositoryEvent + refresh scope，移除无差别全量刷新。
4. 让 capability、通知权限和安全凭据状态来自真实运行环境。
5. 完成 Project colors、File History 分页取消和批量结果呈现。
6. 对齐 Submodule 现有命令、分支状态菜单和 gitlink 操作，并回归右键菜单与全部 Diff 类型。
7. 完成多工作区、多窗口、国际化和可访问性收口。
8. 执行 macOS、Windows、Linux 安装包与 Runtime 验收，记录真实边界。

每一步都应在完成后关闭对应差距，不创建新的长期并存旧状态路径。涉及公共契约时先调整 Rust/Specta 类型，再同步 Bridge、Store、UI 和测试。

## 14. 最终验收标准

V4 完成时必须同时满足：

- 非 AI 可见功能没有 Mock、空操作、错误目标或只存在 UI 的入口。
- 不存在由单个全局 `busy` 导致的跨仓库、跨面板误阻塞。
- Watcher、定时器和操作结果按 workspace/repository/domain 精确更新。
- 所有长任务可正确取消，旧请求无法污染当前上下文。
- capability、通知权限和安全凭据状态与真实平台一致。
- 批量操作完整保留并展示每个仓库的部分成功结果。
- Project colors 在实际 UI 中生效，File History 分页不存在串数据。
- Submodule 只保留现有命令、分支状态菜单和 gitlink 的 Stage/Unstage/Refresh，不出现独立标签、面板或额外右键管理菜单。

## 15. 定义修正与验收记录

为避免实现与 Tauri 运行模型冲突，V4 使用以下可执行定义：

- 对前端公开的 Bootstrap 结果是 Rust Backend 与 Tauri 平台插件共同汇总的运行时真值。通知权限由原生通知插件读取，不能由 Rust 根据操作系统名称猜测。
- `DesktopCapabilities` 和 `RepositoryCapabilities` 的 `availability` 是界面判断真值；原布尔字段暂时保留用于状态迁移和旧快照兼容，不得作为新入口的唯一判断依据。
- Watcher 能定位现有仓库时必须发 repository scope；新增、删除、移动或无法安全归属的路径允许降级为 `workspaceSnapshot`，不得把不确定事件错误投递给其他仓库。
- Project color 使用稳定 ID。显式删除且路径仍可访问时清理 workspace 和 repository 映射；路径离线时保留 repository 映射，避免临时磁盘或网络路径不可用导致用户配置丢失。
- 安全存储能力探测必须有超时，只使用应用专属随机探测项，并在同一进程内缓存结果；测试使用内存实现，不触碰用户真实凭据。
- 多窗口自动刷新、启动 Fetch 和通知使用共享 lease 去重；lease 只负责调度去重，写操作安全仍由 Backend operation coordinator 保证。
