# VersionDock 发布准备

完成可供审阅的本地发布准备，由当前 Codex 直接整理与翻译内容，无需额外 AI API、密钥或依赖。

## 确定范围与版本

- 从当前 Git 仓库根目录操作，先读 `git status --short`、`package.json`、`src/release-notes.json` 和 [发布维护指南](../../../docs/release-publishing.md)，保留用户已有改动。
- 用户要求“准备发布”时，同步版本、生成说明并执行本地校验。按明确版本号或 patch/minor/major 操作；未指定时采用 patch，先简短告知这一假设。
- 如果当前版本尚未打标签且已经高于上次版本，优先继续准备当前版本，避免重复调用导致再次递增；用户明确要求另一个版本时遵从其要求。
- 用户只要求“生成／修改更新说明”时，不修改版本元数据。优先整理当前未打标签的版本；当前版本已有标签时，为下一个 patch 版本生成记录并说明尚未同步版本。
- 只接受正式版本 `X.Y.Z`，目标版本应高于基线版本。已有版本标签的记录视为不可随意重写；核查用户是否明确要求修订历史记录。
- 创建 Skill 或解释用法本身不触发版本递增或发布准备。

## 收集真实变更

1. 优先使用用户指定的上次发布标签。否则通过 `git tag --merged HEAD --sort=-version:refname` 列举当前历史中的标签，只保留正式 `vX.Y.Z`，选取低于目标版本的最高版本作为基线。用 `git merge-base --is-ancestor` 验证基线在当前历史中。
2. 本地标签仅表示已有版本边界，不证明远程发布成功。有明显缺失、浅克隆或标签与历史记录不一致时，先核查；有远程读取能力时可以查询，无法确定基线才向用户询问。首次发布按现有实现整理，不凭空指定旧标签。
3. 读取基线到 `HEAD` 的提交标题和正文，以及累计 diff。先查看变更文件列表，再读取与用户行为相关的源码，避免大型资源或文档删除淹没实际产品变更。例如：

   ```bash
   git log --reverse --format='%h %s%n%b' BASE_TAG..HEAD
   git diff --name-status BASE_TAG HEAD
   git diff BASE_TAG HEAD -- src src-tauri scripts .github
   ```

   将 `BASE_TAG` 替换为实际验证的标签。差异很大时按模块读取；最终以累计差异为准，合并重复提交，排除已撤销的改动。
4. 准备发布默认包含当前工作区中的产品改动：分别检查暂存区、未暂存 diff 及相关未跟踪源码，并说明它们尚未提交。用户指定仅已提交内容或具体提交时，严格按该边界生成。不要清理、暂存或提交无关文件。
5. 对关键条目保留简短的“说明 → 提交或文件”依据，在交付时用于说明，不额外写入 JSON。提交信息只是线索，不能作为功能完成的唯一证据。

## 编写双语说明

- 面向使用者描述可感知的功能、修复和改进，优先说清具体场景与行为变化。例如把“修复目录扫描错误处理”写成“扫描工作区时跳过无权限访问的子目录，并提示根目录访问失败的原因”。只有实现支持这些细节时才这样表述。
- 按功能合并相关改动，通常整理成 3～6 条；小版本只有一条真实变化也可以，不凑数量。
- 默认排除纯文档、测试、格式、内部重构、Skill 维护及无用户影响的 CI 调整。涉及安装、下载、更新或平台兼容的发布改动可以保留。不要仅根据 commit type 排除，因为 `chore` 也可能影响使用者。
- 不暴露内部地址、凭据、实现路径或无需用户了解的技术细节。不编造功能，不把未实现、占位或仅通过静态检查的能力写成已交付。
- 中英文条目按相同顺序逐条对应，含义与数量一致。中文简洁自然，英文自然翻译，Git、SVN、macOS 等专有名词保留。
- 没有任何可对外说明的变化时，报告事实并澄清是否仍需发布；不要写“修复若干问题”“优化性能”等无依据的填充内容。

## 写入与校验

1. 先确定目标版本、基线和说明内容，再修改文件。准备发布时复用 `npm run version:bump -- TARGET_VERSION` 同步 package、Tauri、Cargo 及锁文件；传入明确目标版本以便重复运行。已是目标版本时不重复递增。
2. 在 `src/release-notes.json` 首部添加目标记录；同一未发布版本已经有记录时，基于真实差异更新该条并保留人工补充，不新增重复项。保留历史记录和原有排版，写入后保留文件末尾换行。
3. 记录包含 `version`、`date`、`highlights.zh-CN` 和 `highlights.en`。日期采用用户上下文时区的当天日期或用户指定发布日期，格式为 `YYYY-MM-DD`。两种语言都是非空字符串数组，每条不含换行。例如：

   ```json
   {
     "version": "0.2.0",
     "date": "2026-10-07",
     "highlights": {
       "zh-CN": ["修复扫描工作区时因子目录无权限而中断的问题。"],
       "en": ["Fix workspace scans stopping when a subdirectory is inaccessible."]
     }
   }
   ```

   示例仅展示格式，实际版本、日期与内容必须从本次任务得出。
4. 准备发布运行 `npm run check:metadata`、`npm run test:release` 和 `git diff --check`。如果本次任务还包含实现改动或用户要求完整发布检查，按维护指南运行 `npm run check`；已有同一状态的通过结果可以复用，避免无意义重跑。
5. 只生成说明且未同步版本时，直接调用 `scripts/release-notes.mjs` 的 `validateReleaseNotes` 校验整个 JSON，并用 `releaseNotesForVersion` 验证目标条目，不把当前元数据校验通过当作目标版本校验通过。
6. 报告目标版本、变更基线、生成的中文条目、改动文件以及实际通过的检查。区分“说明已生成”“本地发布准备完成”“完整检查通过”和“已公开发布”，不把静态检查描述为真实安装／更新验证。

## 提交与实际发布

本 Skill 默认完成本地准备。是否提交、创建标签、推送或触发工作流由用户本次及此前仍有效的指令决定；已获授权的动作继续执行，不重复询问。用户仅说“准备发布”不自动等同于“公开发布”。

用户明确授权实际发布时，按 [发布维护指南](../../../docs/release-publishing.md) 及 `.github/workflows/release.yml` 完成检查、提交、标签和推送；涉及依赖、工具链或工作流改动时遵守缓存预热步骤。执行前核查目标版本和远程状态，拒绝覆盖已公开版本或移动已有标签。发生失败时保留本地结果，按指南判断可重试范围，不反复重建或覆盖已发布产物。
